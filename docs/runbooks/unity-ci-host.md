# Unity CI pool hosts

Operating the hosts of the org-wide Unity runner pool (label `unity`). Which jobs run where: unity-core-playground `docs/operations/ci.md`. Slot counts, cores and memory caps: [`ansible/inventory.yml`](../../ansible/inventory.yml) (`unity_ci_runners`, `unity_ci_mac_runners`, `ci_hosts`); how many slots may take work at once: [`apps/ci-runner-governor/config.json`](../../apps/ci-runner-governor/config.json).

## Apply the play

- From `ansible/`: `ansible-playbook playbooks/site.yml --limit <host> --tags unity-ci` (play "CI runners (Unity slots and the seats that borrow them)", roles `ci-host` and `github-actions-runner-linux`). The workstation's `gh` mints the org registration token and needs `admin:org` (`gh auth refresh -h github.com -s admin:org`).
- Each slot is its own runner under the `actions-runner` user in `/var/lib/actions-runner/unity-pool-<n>`, its HOME, so slots never share a Unity cache, a `Library/` or `~/.ssh`. They do share one asset-library LFS store, `/var/lib/actions-runner/.cache/bnb/asset-library-lfs` (`ASSET_LIBRARY_LFS_STORE`), so a new slot does not download the whole library first. `ci-host` seeds that store from the workstation's `~/.cache/bnb/asset-library-lfs` (`tasks/lfs-store.yml`: rsync on the LAN, S3 off it), and re-runs skip an unchanged store by its fingerprint.
- Lowering `unity_ci_slots` does not remove a slot; the steps are in the play's header comment in `site.yml`.
- A new host goes into the inventory only; re-run `scripts/render-ci-topology.py` and commit `apps/ci-topology/topology.json` with it (CI fails when it is stale). The exporter and governor read their slots from that file; the governor's `config.json` holds only thresholds, power and rates.

## Unity activation

- A host is one activation whatever its slot count: every slot mounts one machine id, `/var/lib/actions-runner/unity-machine-id`. Deleting it makes the host a new machine.
- Every host activates on the shared Unity Personal serial. No per-machine cap has shown up; the limit hit is many activations at once (about 15 in 90 minutes got "Found 0 entitlement groups"), so add hosts one at a time.
- The first job on a new host proves it. If it says "Unity activation failed", in order: return stale activations on the Unity ID portal and rerun, or buy a paid seat or Build Server licenses. Licensing: [unity-ci-hardware.md](../unity-ci-hardware.md#unity-license).

## Keep the host's copies current

- `ci-host` puts the asset-library-hd copy (`/var/lib/actions-runner/asset-library-hd`) and the editor images on each host, copied from the workstation. Re-run it with `--tags unity-ci-host` after asset-library-hd's packages change and on a Unity upgrade.
- Unity upgrade: add the new tags to `unity_ci_images` (`ansible/roles/ci-host/defaults/main.yml`), `docker load` them on the workstation, and run the role on every host before the upgrade merges. The `windows-mono`, `mac-mono` and `android` tags player builds use belong there too, or the build dies pulling its image.
- By hand, when the role cannot run or the workstation's checkout holds an uncommitted change (the role packs all of `Packages/`; tar only the new package folders then), from the workstation:
  - ms-a2 (the slim-tour slot): `tar -C ~/dev/bnb/games/engine/asset-library-hd -cf - Packages | ssh kblack0610@192.168.1.28 'sudo tar -C /var/lib/actions-runner/asset-library-hd -xf - && sudo chown -R actions-runner:actions-runner /var/lib/actions-runner/asset-library-hd'`
  - Then compare `ls Packages | wc -l` and `find Packages -type f | wc -l` on the host with the workstation's.

## Editor images over IPv4

`docker pull` of an editor image fails on the home network: the IPv6 path corrupts long downloads (`tls: bad record MAC`) and docker cannot resume a layer. Until the router is fixed, fetch over IPv4 on the workstation with `scripts/test/fetch-image.py`, which lives in the unity-core-playground repo (run it from that checkout), and load it over ssh:

```sh
scripts/test/fetch-image.py unityci/editor ubuntu-<version>-base-3 ~/.cache/unity-image-fetch/blobs ~/.cache/unity-image-fetch/base && tar -C ~/.cache/unity-image-fetch/base -cf - . | ssh kblack0610@192.168.1.26 'sudo docker load'
```

`<version>` is from the playground's `ProjectSettings/ProjectVersion.txt`; the other tags go the same way. Delete `~/.cache/unity-image-fetch` afterwards.

## Labels

- Every slot carries `unity`, plus `unity-full` while the host's `unity_ci_full` is true (the default). Full runs (nightly, release, Multi) ask for `unity-full`, merge gates for `unity` and `unity-gate`. GitHub has no queue priority, so to reserve a runner for gates, set `unity_ci_full: false` on one host.
- `unity-gate` (`unity_ci_gate`, default false) is on the hosts a merge gate may land on: ms-a2, deskslim-2, deskslim-1, tuf-b550 and cachyos-x8664-main. A Spot host leaves it off, since a reclaim would kill a gate (playground ucp-1778). The governor's withhold swap leaves it alone: a gate also asks for `unity`, which a withheld slot has lost.
- An apply (`--tags unity-ci`, not `--check`) resets every registered slot's labels to the inventory's, `unity_ci_slot_labels` included, with one PUT to the org labels endpoint (role `github-actions-runner-linux`, `tasks/labels.yml`). A slot the governor withholds stays withheld: it keeps its `unity-withheld` or `unity-build-withheld` in place of the pool or build labels. So a label change is an inventory change plus an apply; a label added on the live runner alone is gone after the next apply.
- The workstation (cachyos-x8664-main) has two slots with `unity_ci_full: false`, so it takes merge gates and never a full run. The governor reads that from the topology (`"full": false`), since it re-labels a runner on admit. Each slot has three cores and 16G of its own. A third slot waits for a day of load and temperatures with two. No gate runs anything else here (unity-core-playground `docs/operations/ci.md` rule 2).

## The governor

apps/ci-runner-governor decides which registered slots take jobs and when the cloud hosts run. Its docstring says what it reads and in what order; this section is the rule. The knobs are config.json, the slot layout is the topology, and `replay.py` replays recorded cycles against a change; a refactor of `decide()` runs `replay.py --baseline <master governor.py> --synthetic 20000` and ships with zero differences (its docstring has the command).

- Admitted and withheld: every slot stays registered and warm. An admitted slot carries the labels jobs ask for; a withheld one has them swapped for `unity-withheld` (or `unity-build-withheld`), so it finishes its job and takes no other. A host with `"full": false` gets only `unity` back on admit, never `unity-full`.
- LAN verdicts, per host and cycle: HOT withholds one slot (the idle one first, then the busy one nearest its end), ROOM admits one while pool jobs wait (or a job on one of the slot's shared caps, light or heavy), STEADY does nothing. After an action the host is left alone for `cooldown_seconds`, since a job takes minutes to show in the 5-minute rates. A missing reading is never room.
- Floors and caps: each host keeps its `min_admitted`, and the pool never drops below `pool_min_admitted` (Sentinel's unity-runners-online watch) or admits past `pool_max_admitted` (each admitted slot is a Unity activation, and about 15 in 90 minutes is where activation began failing).
- FULL: a host short of disk loses every slot, one per cycle, past its floor and cooldown, since a Unity job can write tens of GB and kubelet evicts at 5% free (on 2026-10-31 that took monitoring and the pager down for 8 hours). Only the pool floor holds, and the host comes back only above the higher admit line.
- Standby hosts (every cloud host with a Unity slot): overflow, withheld until more jobs wait than the other hosts' idle slots and this cycle's admits can take, then one slot per cycle up to `max_admitted`, back once no job it could take has waited for `dwell_seconds`. Start order, fallback, start, stop, pack and the day cap: "What starts and stops it", under the AWS hosts.
- Groups: a build slot (`unity-build`) or a wide slot (`unity-wide`) leads a slot group and shares its test slots' cores, so a lead and its tests never run at once. A waiting build or wide job claims a free group whose lead can take it, most constrained job first (a release build needs a `unity-release` lead); the admitted test slots step aside in one cycle, and the lead comes in once none is busy. In every other group the lead is withheld and the tests are the pool's. A slot withheld for its pair is exported as `ci_governor_lent` (to tests or build), so dashboards tell it from one held for load.
- Pins: a host's `<host>.slots` key holding `{"slots": N}` (machine-mode), or a live `<host>.reserve` (pins it to 0), moves one slot per cycle toward N in place of the verdict, past the cooldown. The pool floor and cap still hold, and a FULL host keeps its own verdict unless the pin withholds. On a standby host a pin is a lower cap, an "on" override's included. Details: "Pinning a host's slots".
- Lending: a Forgejo or personal-repo seat has no cores of its own; it runs only while the governor lends it the LAN slot it borrows. The kind whose job has waited longest goes first; a slot is lent only on an unpinned host that is not HOT or FULL, one per host per cycle past its cooldown and never past the pool floor, except that a ROOM host lends every idle withheld slot at once. A lend is three steps, each read back from GitHub before the next, so a slot never runs two jobs: lend (the slot's labels go and it is marked `unity-lent`), grant (once withheld, lent and idle: the Forgejo lease turns to forgejo, or the repo seat gets its caps back), return (no job left, an older GitHub job wants it, the host turns unfit, or the supervisor stopped asking; the mark goes once the seat has given the slot back). Each GitHub job that has waited longer than any job of a lend's kind takes one lent slot back even while its seats are busy (they finish the job they hold and take no other), idle lends first, and a lend already going back counts as that job's slot: a steady stream of light jobs never leaves a lend idle, and waiting for idle once left 13 Unity slots lent while playground Tests waited 30 minutes (hc-766). A slot with several Forgejo seats serves as many of them with one lend as their measured weights fit (the weights sum to at most 1, see below), and goes back only once every one has given it back. After a restart a slot that still carries the mark stays lent. A governor that is down lends nothing: Forgejo CI stops, GitHub CI does not.
- `ci_governor_withheld{runner,reason}` says why each withheld slot is held (lent, pin, disk, hot, cooldown, no-work), and `ci_governor_decision{host,verdict,action}` is this cycle's verdict per host.
- CI in slot units (hc-668, `units()`): `ci_governor_capacity_units{host}` counts slots that are busy or not withheld as pin, disk or hot (a hold stops the next job, not the running one); `ci_governor_busy_units{host}` is 1 per busy slot and a lent slot's busy seats at their weights (at most 1); `ci_governor_backlog_units{kind}` sums the waiting jobs' weights (`slot` for a job that takes a whole slot); `ci_governor_drain_seconds` is that backlog times each kind's p50 run time (`github_job_duration_seconds`, the pool's when the kind has none) over total capacity. No drain series means it could not be priced; readers show `-`. The CI chip reads them as `CI 6.4/16 q9 ~12m`. Every topology host has a capacity and busy row, 0 when none of its slots is online: a whole-slot host with no Unity slot (mac-mini) counts each online runner as 1 unit, busy while it runs; a host's local seats (below) add their units to its row, and their waiting runs are `backlog_units{kind="local"}`. The drain stays the pool's, since a local run or a Mac job never waits on pool capacity.
- `ci_governor_kind_weight{kind,measured}` is each job kind's share of a slot, one row per kind while lending runs: the hourly p90 measurement (`kind_weights()`, `measured="true"`), else 1 with `measured="false"` (a kind under `min_samples`, or a whole-slot one). The CI views read their WEIGHT column from it.
- Local seats (`ci_local_seats` in the inventory, the topology's `local_seats`, never slots): a local test run on a LAN Unity host (slots.sh, no forge, no runner) leases a seat named `<host>-local-<n>` through the same `/lease` the Forgejo seats use: `have=github` asks, `have=local` keeps it, `have=done` gives it back, and a seat that stops polling is dropped. A granted run confirms with `have=local` within 30 seconds (`LOCAL_WAIT_GRACE`), or the seat goes back, so a run killed while it waited strands nothing. Grants go to the oldest waiter up to the host's admitted count, which the host's verdict moves one at a time under the host's cooldown, the one slot moves use: FULL or HOT takes one back down to `local_min_admitted`, ROOM with a run waiting adds one up to the seat count. A local pin (the `local` field of the host's `<host>.slots` key, machine-mode's `unity_slots`) sets the count to it at once, at most the seat count and below `local_min_admitted` too, whatever the verdict or cooldown; only FULL still steps down under it, and capacity then counts the admitted seats. Lowering it stops the next run, never a held one; a release reservation pins no local seat. The cost of sharing it: a local step on a ROOM host holds that host's next slot admit for up to `cooldown_seconds`, and the other way round. A held seat is 1 busy unit.
- Forgejo seats name their job (hc-571): a seat reads the task id from its one-job log line and sends it on its lease ask (`&task=`); `GET /tasks` on the governor serves `{seat: task id}`, and github-runner-exporter (`GOVERNOR_URL`) fills a running Forgejo seat's repo, workflow, job, branch and url from that task, or repo `(not watched)` when the task is in no watched repo.

## Slots and seats

On a host whose `ci_caps` carry light, heavy or forgejo, a lendable Unity slot is no kind's alone. It takes Unity jobs, one at a time on its own cores and memory cap, and the governor also lends it to seats, which run the small jobs. A light or heavy job runs on a seat on every host that takes it (`ci_seat_kinds`, hc-693), never on a whole slot: the slots drop each kind their host's seats serve. Only a host without `ci_seat_kinds` would still run light and heavy on whole slots (`SHARED_CAPS` in `scripts/render-ci-topology.py`), and none is left. No runner is kept free for small work, so a small job can wait behind Unity jobs for a slot to lend. The one exception is `jump_lends` in `apps/ci-runner-governor/config.json` (`{"light": 1}`): while fewer than that many lends of the kind are open, a lend may start even though older Unity jobs wait, and the kind's busiest that-many lends are exempt from the age-rule reclaim (not from an unfit host, a stale lease or "no job needs it"). Both stop at `jump_max_seconds` (900): a GitHub job that has waited longer gets no jump lend started against it and takes one back like any lend, so a stream of light jobs holds a Unity job up 15 minutes at most. A playground gate's plan and report jobs are light and are created after other gates' shards are already queued, so under the age rule they waited out the whole Unity queue (report job queue p90 0.7 min before hc-693, 8.8 to 10.6 min after; ucp-2881). It costs at most one Unity slot per jumping kind. A seat is a runner with no cores of its own, so seats add jobs, never cores: a Forgejo seat `<host>-unity-pool-<n>-forgejo` (and `-forgejo-2` and on, one per `MIN_JOB_CORES` of the slot, below), or a personal repo's runner `<host>-dotfiles-private-1` or `<host>-gungan-speak-1` (`ci_repo_runners`, topology `borrows`). Which slots lend, as rendered in `apps/ci-topology/topology.json`:

- tuf-b550: all four slots take unity, 14G each: slots 1 and 2 have three cores (six CPUs), slots 3 and 4 four (eight). Each registers Forgejo, light and heavy seats by slot size (`ci_seat_kinds: [light, heavy]`): three of each on slots 1 and 2, four of each on slots 3 and 4. The repo runners borrow slots 1, 2 and 3.
- deskslim-2: three slots that take unity, with Forgejo, light and heavy seats by slot size (`ci_seat_kinds: [light, heavy]`): three of each on slots 1 and 2 (six CPUs), four of each on slot 3 (eight). The repo runners borrow slots 1, 2 and 3, so a lend to one takes that slot from its seats until the job ends.
- deskslim-1: the same as deskslim-2.
- ms-a2: slots 1-4 take unity, and only slots 1 and 2 lend, with three Forgejo, light and heavy seats each (slots 3 and 4 sit under build slot 5's group and do not lend; the renderer fails a host whose `ci_seat_kinds` have no lendable slot), and there are no repo runners. Slot 5 is unity-build only.
- Not lent: cachyos-x8664-main (`ci_caps: [unity]`) and any cloud host. They take Unity work only, so light and heavy jobs never run there; the renderer fails a cloud host that carries light, heavy or forgejo.

- The governor lends a slot to a seat ("The governor", Lending): it withholds the slot's GitHub labels, waits for it to go idle, then turns the seat's lease to forgejo (or admits the repo runner). The kind whose job has waited longest goes first, and the slot goes back to GitHub when an older GitHub job wants it, busy or not. A running job is never cut off: a busy slot is lent only after it drains. `ci_governor_lent` shows which slots are lent.
- An idle withheld slot on a ROOM host is lent at once, every such slot in one cycle, cooldown or not. Taking a slot from the pool is limited by the per-slot cooldown, one per host per cycle, the pool floor, and a HOT or FULL host, so a Forgejo job waits on those, and on the slot draining, not on the depth of the Unity queue. A returned slot is readmitted to the pool when its host is ROOM and the pool is under its cap. `ci_governor_withheld{runner,reason}` says why each withheld slot is held (lent, pin, disk, hot, cooldown, no-work).
- A Forgejo seat runs `forgejo-runner one-job` only on a forgejo lease, read from the governor's `/lease` long-poll (NodePort 30321). With the governor down every seat holds github and every repo runner stays withheld: Forgejo CI and the personal repos' CI stop, and the org pool's GitHub CI goes on. Seat setup, re-registering and the break-glass merge for a governor fix: `apps/forgejo/README.md`, Runner.
- A Unity job never shares cores with another job: a Unity job and a small one never share a slot, which is the PlayMode timing failure of 2026-10-06 (`ansible/roles/ci-host-budget/defaults/main.yml`). Slots that share cores by design (ms-a2 slot 5 with slots 3 and 4) are kept apart by the governor's group rule (A LAN build slot, below).
- Seat weights: each lendable slot registers `floor(CPUs / MIN_JOB_CORES)` Forgejo seats (`scripts/render-ci-topology.py`; 3 on a 6-core slot), and the governor serves as many of them with one lend as fit while their weights sum to 1. A kind's weight is the larger of its p90 cores over the slot's CPUs and its p90 memory over the slot's MemoryMax (`cc:job_kind_cores`, `cc:job_kind_mem`, `scripts/ci-kind-weights.py`), clamped to the floor and 1, re-read every `refresh_seconds`; the knobs sit in `apps/ci-runner-governor/config.json` "weights". A kind with under `min_samples` samples has no weight and reads 1, one job per slot, as before. The seats past the limit are handed github on `/lease`, so the weight caps running jobs, not only lends. The log line `seat weights {...}` shows what it read. To roll back, revert this change: the governor and `apps/ci-topology/topology.json` go together.
- Light and heavy seats (hc-667): a host's `ci_seat_kinds` (inventory `ci_hosts`, each kind also in its `ci_caps`) registers `<slot>-light-1` and on (or `-heavy-`) on each lendable slot, org runners that start withheld (`light-withheld`) and carry the kind's label only while a lend grants them. The host's Unity slots drop those kinds from their caps, so a job of one waits for a lend (the log shows `lend ... a light job has waited`) and never asks the host for a whole slot, and a lend admits as many seats of the kind as `pack()` lets in, returns them together, and readmits the slot once none runs. A slot that still carries a kind it dropped sheds it at its next admit or withhold (the governor's `moved`), and an apply resets its labels. Every LAN host that takes light or heavy sets it (hc-693, 2026-11-19); `CiSmallJobOnWholeSlot` catches a whole-slot path coming back (A small job on a whole slot, below). Roll back one host: remove its key, re-run `scripts/render-ci-topology.py` and apply; the retired seats' runners stay registered offline, delete them in the org's runner settings and `rm -rf` their dirs under the linux-ci home.
- Repo seats: a `ci_repo_runners` entry `{repo, name, borrows}` registers `<host>-<name>-1` and on, as many as the borrowed slot's Forgejo seats, each carrying the slot's size, so the governor measures the `repo` weight and one lend runs as many of the repo's jobs as `pack()` lets in. With one seat and no size a lend ran one job, and a burst of `.dotfiles-private` PRs (4 to 7 jobs each) queued behind it (2026-11-20). The `repo` weight is one figure for every personal repo, so a repo heavier than it caps its own count with `seats:` (personal-sites and gungan-speak run one each; per-repo weights would need a governor change). After the merge, apply `--tags linux-ci` on deskslim-2, tuf-b550 and deskslim-1 to register the new seats; `CiHostRunnersOffline` reads them missing until then.
- Each slot keeps its own home and `_work`. A Unity repo's light job parks the warm Library first (`ci-fresh-workspace`, under Disk).
- Forgejo wait has a p90 in the exporter (`github_job_queue_seconds{forge="forgejo",pool="forgejo"}`). `scripts/ci-pool-idle.py` reports idle slot-hours per host while a kind the slot cannot take waited (its caps from `github_runner_pool_slot`); for a 7-day window read VictoriaMetrics, not Prometheus (the port-forward and command are in the script's docstring).
- `scripts/ci-kind-weights.py` reports each job kind's measured share of a slot: cores and memory p50 and p90, each over the slot it ran on (from `ci_unity_slot_cpus` and `ci_unity_slot_memory_max`), and a weight, the larger p90 share. It reads `cc:job_kind_cores` and `cc:job_kind_mem`, a runner's measured use labelled by the exporter's `ci_runner_job{runner,kind}`; a kind with no samples prints `-`.

## The AWS hosts (aws-spot-1..3, aws-build-1)

No cloud host is in the pool. The four AWS hosts left the inventory, topology, governor config and node scrape on 2026-11-19, after EC2 stopped knowing their instances (the governor logged `no instance` every cycle and NodeDown paged for aws-build-1). This section and "The AWS build host" below describe the standby mechanism the governor still carries, for a cloud host added back the same way.

- Every AWS host is one instance from the platform repo's `infra/aws-ci-burst` Terraform module. Each has its own data volume (`/var/lib/actions-runner`, `/var/lib/docker`, `/var/lib/containerd`, label `ci-data`), and that volume and the machine id survive a stop and start; a stopped instance costs only its disks. aws-build-1 is the player-build lane (below).
- The on-demand burst hosts aws-burst-1, -2 and -3 (m7a.8xlarge, $1.855/h, 17 slots between them) were retired on 2026-11-16 at the human's request, once ms-a2 and deskslim-2 were in the pool. Pool overflow is now Spot only, when AWS has Spot room. To bring an on-demand host back: a `hosts` entry in the platform module, an apply, the inventory entry and a re-rendered topology, governor `config.json` `rates` and `power` entries, then the play.
- aws-spot-1 (m6a.8xlarge, us-east-2c), aws-spot-2 (m7i.8xlarge) and aws-spot-3 (m6i.8xlarge), added 2026-11-13, are persistent Spot, one instance type each, $0.28 to $0.77 an hour. These types have 16 cores with SMT (vCPU n and n+16 share core n), so 5 slots of 3 cores and 16G each, pinned as `1-3,17-19` and so on. They have no `unity-gate`, since a reclaim kills every job on the host (ucp-1778). `CiSpotHostReclaimedOften` warns when one is reclaimed more than 3 times in 24 h; then set it `spot = false` in platform `infra/aws-ci-burst/variables.tf`.
- Admin access is SSH through SSM, no inbound port: `ssh -o ProxyCommand='aws ssm start-session --profile bnb --region us-east-2 --target %h --document-name AWS-StartSSHSession --parameters portNumber=%p' ubuntu@<instance-id>`. The instance id is in `ansible/inventory.yml`.
- Labels name a need (unity-core-playground `docs/operations/ci.md#the-runner-pool`): `unity-wide` (`unity_ci_wide`, default false) marks a slot with the CPU for Multi, Soak and Playloop, and only slots that passed the ucp-1521 probes carry it (none since razer-laptop left the pool on 2026-11-17: Multi, Soak and Playloop wait until a cooler host passes those probes, hc-544; ms-a2 runs 90 to 99.5C under CI, so it does not carry it; one slot alone can carry it through `unity_ci_slot_labels`, or a wide group lead, "A wide slot on an owned host" below), and a wide slot needs 20G of memory, which `scripts/render-ci-topology.py` checks, so the Spot hosts' 16G slots stay plain (playground ucp-1830; to widen them, raise `ci_unity_slot_memory_max` to 20G first, then the flag and the live label); `hd-library` (`unity_ci_hd_library`, default `unity_ci_lan`) marks a host holding asset-library-hd; `slim-tour` (`unity_ci_slot_labels`) is the one slot playground slim-tour.yml runs on, whose warm trees the prune keeps (Disk, below). A new label goes on the inventory flag, and the next apply puts it on the live runners. Add a label here before a playground workflow asks for it.
- Off the LAN: no `lan` label (`unity_ci_lan: false`), and the libraries come through S3 (`unity_ci_library_s3`) instead of a tarball over ssh. So does the shared asset-library LFS store (`tasks/lfs-store.yml`, prefix `asset-library-lfs/objects`; a LAN host gets it over rsync), seeded from the workstation's `~/.cache/bnb/asset-library-lfs`: a cold release tree fetching about 4 GB of LFS through the Cloudflare tunnel ended in `batch response: Authorization error` (aws-build-1, run 42905629793). Re-run `--tags unity-ci-host` after the asset-library pin moves and the workstation has pulled it, or a release fetches the new objects through the tunnel.
- Each slot's first job imports its `Library/` cold, about 50 minutes; later jobs are warm (a PlayMode batch ran 10 minutes, against about 12 warm on mac-studio).
- Watch jobs from the host. The GitHub jobs API shares one 5000/h limit with every session, and polling it drained that limit on 2026-11-03: `sudo journalctl -f -n 0 -u "actions.runner.*" | grep -E "Running job|completed with result"`.
- A change to a runner unit or its `.env` restarts the slot, and the apply never cancels a job for it: under a job it drains the slot (every custom label removed through the org labels endpoint, so `host-<host>`, `hd-library` and `unity-gate` jobs stop landing too), waits for the job to end, restarts the slot and puts its labels back (`roles/github-actions-runner-linux/tasks/drain.yml`). ### What starts and stops it

apps/ci-runner-governor powers it (the inventory's `ci_power` and `ansible_host`, rendered into topology.json `power`, with config.json `power` -> `<host>` for its knobs; every cloud host with a Unity slot in the topology is a standby host, cheapest `rates` first). The rule is "The governor" above; in short:

- Order: `standby` is a list, and the governor starts its hosts in that order: `aws-spot-1`, `aws-spot-2`, `aws-spot-3`, cheapest Spot first, then `aws-build-1`, whose six test slots are the last overflow. A Spot host that has no capacity or is reclaimed is passed over for `fallback_seconds`, and the next host takes the queue. Three instance types are why the Spot hosts should not all fail together. A host further down starts only for the jobs the hosts ahead cannot take, so a short queue starts one host and a deep one starts all of them.
- Fallback: a stopped host whose start EC2 refuses (`InsufficientInstanceCapacity` is `capacity`; any other EC2 code, such as a Spot price or request state or a vCPU limit, is `refused`), or that AWS stops (a Spot reclaim, or a start that found no capacity after all: any `Server.*` state reason, `reclaim`), is passed over for `fallback_seconds` (3600), and the next host takes the queue at once. AWS restarting a persistent Spot host by itself ends the pass-over. `ci_governor_fallback_total{host,reason="capacity|refused|reclaim"}` counts each pass-over once, `ci_governor_power_fallback_until{host}` is its end, and a reclaim shows as `reason="reclaim"` on `ci_governor_power_state`. Not a fallback: the budget deny policy (`UnauthorizedOperation`), which covers every host, and a network error.

- Start: at least `start_min_excess` (4) waiting jobs it can take past what the other hosts cover, held for `start_after_seconds` (300); `start_now_excess` (8) or more starts it at once. A short burst never starts it. Its slots count as room only once their runners are online.
- Stop: no slot busy for `idle_off_seconds` (900; the warm host, the running unpacked burst host busy last, waits `warm_idle_off_seconds`, 2700, so the next burst does not wait on a cold start), or `max_hours_day` hours run this UTC day: 24 on the AWS hosts since 2026-11-11, so no day cap, while they stand in for the Mac Studio; the monthly AWS budget action still stops them. It withholds one slot per cycle and stops the instance only once no slot is busy, so a stop never kills a job.
- The day's hours reset at UTC midnight. After a pod restart the governor reads back the highest `ci_governor_power_hours_today` it exported that day and the newest reason other than `none` (a running instance: since its EC2 launch; a stopped one: today), so a deploy resets neither the cap nor the reason (a host first seen already running, started outside the governor, keeps `none` until its next start); with Prometheus unreachable it counts from the EC2 launch time and logs `earlier run time and cause unread`.
- Pack: with two or more burst hosts running and no waiting job one of them can take, the least busy live one (tie: the one started last) has its slots withheld and stops through its idle rule. One at a time, never the last running host, never the only one with a `pack_keep_labels` label (`unity-wide`), never one a waiting job needs. It comes back at once when a waiting job has no other taker or more of its jobs wait than the other hosts have free slots, otherwise after `dwell_seconds` (600). The log shows `pack <host>: ...` and `unpack <host>: ...`, then its withholds and stop under verdict `PACKED`.
- Pack, measured 2026-11-16 (48 h after #946, 11-13 16:40 to 11-15 16:40 PST): 45 packs and 32 unpacks, 14 of the unpacks within 10 min of their pack, so about 4 in 10 packs were wrong at the time; no slowdown from packing (PlayMode shard median 10.3 to 10.5 min with 4 to 6 of 6 slots busy, 11.4 with 3 or fewer, p90 22.9 to 26.4 at full); AWS $ per busy slot-h about 0.70 (uptime x rate over busy job-hours), no better than the 0.56 of 11-12 on the same method. Cost Explorer shows $0 from 11-14, so the budget's `actual` sat at 406.18 for those days and `aws ce` cannot price the window. Numbers and method: plan `that-s-not-encapsulated-minsky` Results.
- Dwell: a standby slot goes back only once no job it could take has waited for `dwell_seconds`, counted from the governor's start after a restart, since the queue reads 0 for a minute between bursts. A standby host without a `power` block has no dwell.
- The Infra page's Rule column shows where the rule stands, from the governor's own numbers: running, "busy" or "idle 6 of 15 min, then stops"; stopped, "2 jobs past the home hosts, starts at 4" or "held 2 of 5 min, then starts"; the day cap or an override when one applies. The governor panel under it shows, per host, its verdict and action, and its admitted slots.
- It needs the `ci-governor` IAM user's key (`ec2:StartInstances`, `ec2:StopInstances`, `ec2:DescribeInstances` on this instance) as `aws-access-key-id` and `aws-secret-access-key` in `ci-runner-governor-secret.yaml`. Without them it logs `power hook off` and does nothing.

### The override ConfigMap

- ConfigMap `ci-runner-governor-override` in `monitoring` holds human and fleet intent, one key family per writer, each key `<host>.<family>` holding one JSON object: `<host>.power` `{"action":"on"|"off","until":<epoch>}` (agent-web), `<host>.slots` `{"slots":N,"local":M,"by":"<who>"}` (machine-mode, the one family with no end; `local` is optional and pins a host's local seats) and `<host>.reserve` `{"until":<epoch>}` (machine-mode release-lane). The contract is `apps/ci-runner-governor/override.schema.json`: the governor reads every key through it and ignores (and logs) a key that breaks it, and a writer's test checks what it writes with `python3 apps/ci-runner-governor/governor.py check-override <key> '<value>'`.
- Every writer changes only its own key, with `kubectl patch --type merge` (a `null` value removes the key), creating the ConfigMap with `kubectl create configmap` only when it does not exist. Never `kubectl apply` the whole object: a get-then-apply drops what another writer set in between.
- It is not in Flux; the governor mounts it optional and ignores an expired or unreadable key. It reads only `<host>.<family>` keys; a bare `<host>` key (the shape before hc-651) is ignored.
- Power: "on" starts the host and keeps it past idle-off and the day cap, for at most `override_on_max_hours` (12, config.json) from when the governor first sees that end time, so a hand-written long "on" cannot hold a host up all day; "off" drains, stops and keeps it stopped.
- By hand: `kubectl -n monitoring patch configmap ci-runner-governor-override --type merge -p "{\"data\":{\"aws-spot-1.power\":\"{\\\"action\\\":\\\"off\\\",\\\"until\\\":$(( $(date +%s) + 6*3600 ))}\"}}"`, and the same patch with `"aws-spot-1.power":null` hands the host back.
- Metrics: `ci_governor_power_state{host,state,reason}`, `ci_governor_power_hours_today`, `ci_governor_power_max_hours_day` and `ci_governor_power_override{action}` (the override's end, 0 with none). The rule's progress: `_power_idle_seconds` of `_power_idle_off_seconds`, `_power_want` of `_power_start_min_excess`, `_power_held_seconds` of `_power_start_after_seconds`, `_power_last_change{action}` (epoch) and `_power_usd_per_hour` (config.json). They exist only while the power hook is on.

### Pinning a host's slots

- `machine-mode reserved|shared|open` on the workstation merge-patches `{"slots":N,"local":M,"by":"machine-mode <mode>"}` into its `<host>.slots` key in the same ConfigMap: 0, 1 or 2 slots admitted, and M local seats (its `unity_slots` column). The mode's table is the command's data file, in the dotfiles repo. `ci_governor_effective_slots{host,source}` is where the host is moving (source `slots` or `reserve` while the governor obeys the pin; `governor`, at what it admits now, when unpinned, or when a FULL host or a standby cap overrules the pin), which `machine-mode` shows.
- A pinned host moves one slot per cycle toward N, past its cooldown and in either direction. A busy slot finishes its job first. The pool floor and cap still hold, and a FULL host keeps its verdict.
- The pin has no end time. A host with no pin, or an unreadable one, is back on its verdict.
- The log says `PINNED`, and `ci_governor_decision{verdict="PINNED"}` shows it.
- On a standby (AWS) host a pin is a lower cap that also holds under an "on" override: `kubectl -n monitoring patch cm ci-runner-governor-override --type merge -p '{"data":{"aws-spot-1.slots":"{\"slots\":0,\"by\":\"hand\"}"}}'`, and the same patch with `null` lifts it. An apply that restarts slots needs no pin; it drains each slot itself (above).

### The month's budget

- AWS Budgets `ci-burst-monthly` (platform `infra/aws-ci-burst`: the limit is `budget_monthly_usd`, the alerts `budget_alerts_usd`, in `variables.tf`) mails the alert address at each alert amount, actual and forecast.
- The Infra page shows the month: AWS's actual and forecast against the limit, the alert and action thresholds, and today's hours times `usd_per_hour`. The governor reads the budget once an hour with its own key (`budgets:ViewBudget` on this budget only, platform `iam.tf`) and exports `ci_governor_budget_usd{kind="actual|forecast|limit"}`, `_budget_alert{basis,usd}`, `_budget_action_usd{type,status}`, `_budget_updated` (AWS's last refresh, a few times a day) and `_budget_ok`. A failed read keeps the last numbers and never changes a power decision. AWS's forecast can sit below actual early in an account's life; the page flags it.
- At `budget_stop_usd` actual it runs two actions on its own: an SSM stop of this instance, and attaching IAM policy `ci-burst-deny-start` (deny `ec2:StartInstances`) to `ci-governor`, so the governor cannot start it again. The governor then logs failed starts; that is expected.
- Budget actions do not undo themselves at the new month. To reverse one (Budget stop): detach the policy, `aws iam detach-user-policy --user-name ci-governor --policy-arn arn:aws:iam::311141527647:policy/ci-burst-deny-start --profile bnb`; find the action ids with `aws budgets describe-budget-actions-for-budget --account-id 311141527647 --budget-name ci-burst-monthly --profile bnb`; for each, `aws budgets execute-budget-action --account-id 311141527647 --budget-name ci-burst-monthly --action-id <id> --execution-type REVERSE_BUDGET_ACTION --profile bnb`. The governor starts the instance at the next deep queue, or start it by hand.

## The AWS build host (aws-build-1)

- The player-build lane, and test slots between builds: an on-demand m7a.8xlarge (us-east-2, 900G data volume, platform `data_volume_gb`) from the platform `infra/aws-ci-burst` `hosts` map. Nine slots (`unity_ci_slots: 9`): build slots 1-3 have 10 cores and 36G each (cores 1-10, 11-20, 21-30), and test slots 4-9 have 5 cores and 16G each (cores 1-5, 6-10, 11-15, 16-20, 21-25, 26-30). Slots 1-3 are the keys of `unity_ci_slot_groups`, which makes them build slots: they get `unity-build` and no `unity`, `unity-full` or `unity-gate`, so no gate or nightly lands on a build slot; slots 4-9 carry `unity`, `unity-full` and `unity-gate`, no `lan` and no `unity-wide`. release.yml asks for `[self-hosted, linux, unity-build, unity-release]`; its `host` input pins a build to another host instead (the razer release lane).
- Each build slot shares its cores with two test slots, so the governor pairs them (inventory `unity_ci_slot_groups`, rendered into the topology: 1 with 4-5, 2 with 6-7, 3 with 8-9) and never runs a build and a test in one pair. A busy build slot keeps its pair. A waiting build claims a pair, the most constrained first (a release needs slot 1 or 2), and both its test slots step aside in one cycle (withheld, `unity-withheld`; a busy one finishes its job), then the build slot is admitted. Every other build slot is withheld (`unity-build-withheld`), and its two test slots are pool slots under the governor's usual rules. Labels never move between kinds: each slot is admitted or withheld with its own. A pair's tests take 32G, under the build slot's 36G, so the host never commits more than its build slots alone; `scripts/render-ci-topology.py` fails a pair whose test slot is off its build slot's cores or over its memory, and any two slots that share cores without a pair.
- The governor powers it as the last standby host: one waiting build starts it after 60 s, tests start it on the pool thresholds (4 jobs past the other hosts for 300 s, as the burst hosts), and it stops 15 minutes after its last busy slot. A `slots` pin caps its test slots only. The exporter counts slots 1-3 as pool `unity-build` and 4-9 as `unity` (the topology has both), so a build's wait stays out of the gate pool's numbers.
- Measured live 2026-11-15 (hc-318): a perf-round build (two jobs) stepped pairs 1 and 3 aside in one cycle at 02:41 UTC, and each build slot came in one cycle after its last test job ended (pool-3 at 02:44, pool-1 at 02:52, after an EditMode shard on pool-4), while pair 2's slots kept serving tests. - Slots 1 and 2 also carry `unity-release` (`unity_ci_slot_labels`), which playground `release.yml` asks for along with `unity-build` (the label the governor and its withhold key on), so releases share those two and `players.yml`, which asks only `unity-build`, always has slot 3. `scripts/render-ci-topology.py` fails the pool when its `unity-release` build slots are none or all (ms-a2 slot 5 has none). - Another build host: one `hosts` entry in Terraform, one inventory entry modeled on this one (its `unity_ci_slot_groups`, whose keys are its build slots), its `ci_power` (provider, region; the instance id is its `ansible_host`), a `rates` entry and any power knobs in the governor's config.json, and a re-rendered topology. `scripts/render-ci-topology.py` checks the slot groups fit the cores.

## Disk

The hourly `linux-ci-docker-cleanup.timer` runs `/usr/local/lib/linux-ci/ci-disk-prune.sh` (roles/ci-host, `tasks/disk.yml`) on every Linux CI host, Unity-only ones too. On idle slots it removes release trees, player trees (`Builds/players-tree/*`) and HD trees (`Builds/hd-tree`, 26G, kept by hd.yml) not touched in 7 days and every copy of one but the newest; then, while the disk is under 35% free, idle slots' warm trees oldest first. If space is still below that floor, it removes idle Unity checkouts' `Builds/players`, `Builds/server` and `Builds/two-process` outputs, then `Library/Bee`, `Library/BuildCache` and `Library/PlayerDataCache`, oldest first within each group. Downloads or builds recreate those outputs; Unity recreates the build caches. `Library/Artifacts`, source checkouts and the container home containing activation state stay. These extra paths have no age or copy eviction above the floor. The slot labelled `slim-tour` (ms-a2's slot 1 since 2026-11-17, `unity_ci_slot_labels`) holds `.keep-warm-trees` (site.yml writes it), so its trees skip the age and copy rules and go under low disk only after every other slot's, and only under 30% free, so one build on top still ends near the governor's 20% withhold line: Slim tour runs by hand before a cut, and each cold run spent 107 to 125 min importing (playground ucp-1884). To move it, move the label and apply `--tags unity-ci`. Every Unity slot also runs it as its job-started hook (`job-started.sh`, which runs `--before-job` on a slot with `CI_SLOT_UNITY=1`): under 35% free it prunes idle slots' trees before the job writes, and above it does nothing. That hook is what holds the AWS hosts back: the governor withholds a host's Unity slots under 20% free and re-admits them at 25% (`ci_governor_disk_held`), but its disk reading is node_exporter's `/`, and Prometheus has none for aws-build-1, whose slots write to `/var/lib/ci`. On aws-burst-1 the hook does the work. Its data volume (`/var/lib/ci`, also mounted at `/var/lib/actions-runner`; `df -h /var/lib/ci`) read 393G size, 305G used and 69G available on 2026-11-15. The runner homes held 232G and containerd 73G; pool 1 alone held 9.9G of player outputs and a 24G main Library (7.5G Bee, 1.5G BuildCache, 2.1G PlayerDataCache). Those paths refill without alternate warm trees, so pruning only release and HD trees missed them. Every busy slot stays untouched, so a host with all slots busy may remain below the floor until a slot finishes. A lock on the runner home keeps the hook and the timer from pruning at once. Changing a slot's hook env restarts the runner and kills its job, so apply it with the host's slots idle. Check it with `systemctl list-timers linux-ci-docker-cleanup.timer` and `journalctl -u linux-ci-docker-cleanup.service`. On razer-laptop the forgejo-runner pod's dind store is also on `/`: it has a 60Gi limit and a prune sidecar (apps/forgejo/README.md, Runner).

What each slot holds is a metric, so read it before running `du` by hand: `ci-runner-disk.timer` (roles/ci-runner-cpu) runs `ci-runner-cpu --disk` hourly on every Linux CI host, at idle IO priority, and writes the bytes under each runner's working directory (checkout, warm Library, `_work`, `_warm`) to `ci_runner_disk.prom`. Prometheus keeps it as `cc:runner_disk_bytes{host,runner}` for two hours after the last run, and `cc:runner_disk_age_seconds` says how old it is; `cc:host_disk_avail_bytes` and `cc:host_disk_size_bytes` are the host's emptiest real filesystem, the one the disk ratio reads. The machine page (agent-web `#infra/machines/<host>`, hub `--tab infra`) and the Grafana `kb-ci-runners` Runners table show both. A slot with no figure (a mac slot, or a host whose timer stopped) shows no data, never 0. Check the timer with `systemctl list-timers ci-runner-disk.timer`.

A Unity slot also takes a Unity repo's light jobs, whose checkout (`clean: true`, sometimes sparse) would wipe or break the warm Library in the same workspace. Such a job runs `ci-fresh-workspace` (`/usr/local/bin`, `files/ci-fresh-workspace.sh`) as its first step. In a Unity checkout it moves every untracked path (Library, Logs, UserSettings, `Packages/packages-lock.json`, ...) to `$HOME/_warm/<repo>/<repo>` and lists them in `<repo>.paths` beside it, so the job's checkout stays incremental (1-3 s, where a fresh clone took 42 s) and touches none of it. The job hook (`ci-fresh-workspace --job-hook`, which also owns the keep-or-empty rule) moves every parked path back at job end and, for a job whose end never ran, at the next job start of any repo; when the checkout is gone it drops the state instead. A path under `_warm` therefore means a light job is running on that slot or one died there. A slot without the hook env refuses to park and fails the step, so a Library is never orphaned.

A host that goes down under a Unity job (a hard reset, a power cut) leaves zero-byte artifacts in that slot's warm Library, and every later job on the slot fails on them with `Error loading the file 'VirtualArtifacts/Primary/<hash>'. File is either empty or corrupted` (tuf-b550's pool-4, twice on 2026-11-20, playground runs 44821730840 and 44849225429). The job hook guards it with a stamp: each job start writes `<boot_id> <workspace>` to `~/.ci-job-boot` in the slot's HOME and job end removes it. A job start that finds a stamp from an earlier boot removes every Unity `Library/` in that workspace, release trees included, and logs `the host went down during the last job`; that slot's next job imports cold, about 50 minutes. A reboot between jobs leaves no stamp and keeps the Library. To clear a torn Library by hand (a slot that predates the stamp): withhold the slot, `sudo -u actions-runner rm -rf /var/lib/actions-runner/unity-pool-<n>/_work/<repo>/<repo>/Library`, and put the labels back.

A change to `ci-disk-prune.sh`, `ci-fresh-workspace.sh` or `job-started.sh` reaches a host only when the play runs there: the convergence-check CronJob runs `--check`, so nothing applies it to any host. After such a merge, from `ansible/`: `ansible-playbook playbooks/site.yml --limit unity_ci_runners:mac-mini --tags ci-disk` (without the limit the OpenWrt play's `always` tasks run too). It rewrites the scripts and the timer and restarts no slot, so it is safe with jobs running. A stopped AWS host fails as UNREACHABLE and the run exits 4: apply that host after its next start. To check a Linux host, compare `sha1sum /usr/local/lib/linux-ci/ci-disk-prune.sh` there with `git show forgejo/master:ansible/roles/ci-host/files/ci-disk-prune.sh | sha1sum` (mac-mini runs `ci-tree-prune.sh` from roles/unity-ci-host-mac instead). A host that never had the hook also needs its slots' `ACTIONS_RUNNER_HOOK_JOB_STARTED` env, which only `--tags unity-ci` sets and which restarts the slots: apply it with them idle.

## GitHub API limit

The exporter's token has two 5000-an-hour buckets: `orgs/` calls (runners) and `repos/` calls (runs, jobs). When one hits 0 the exporter backs off until the hour resets, and the governor, which reads the exporter, stops moving Unity slots. `GithubApiRateLow` warns when a bucket stays under 500 for 10 minutes; `CiGovernorBlind` pages once the governor has been blind for 30. To find what spent it, compare `sum by (kind) (increase(github_runner_exporter_api_calls_total[1h]))` with `github_runner_exporter_api_not_modified_total` (free 304s): a cold cache after an exporter restart, or a new repo with a long run history, is the usual spender (`HISTORY_DEADLINE_SECS` in `apps/github-runner-exporter/exporter.py`). Another tool sharing the same token spends it too, and the exporter's counters do not show it.

## Unattended upgrades

Ubuntu CI hosts (the AWS hosts) keep Ubuntu's daily unattended-upgrade, but `ci-host-budget` (`tasks/unattended.yml`) sets needrestart to list services and never restart them, and holds Ubuntu's docker.io, docker-buildx, containerd and runc out of it. Without that, the 2026-11-13 14:03Z libc6 upgrade on windows-media-ci (an Ubuntu VM, since retired) restarted all three runners several times in four minutes and killed about 40 jobs. A host is covered only once the play has run there; after a change, from `ansible/`: `ansible-playbook playbooks/site.yml --limit unity_ci_runners --tags unattended` (runs only the three tasks in that file, which write config and restart nothing; Arch hosts skip them). Upgrade the held packages by hand when the host's runners are idle (`pgrep -x Runner.Worker` prints nothing): `sudo apt-get install --only-upgrade docker.io docker-buildx containerd runc`. `sudo needrestart -b` lists the services still on old libraries, which a reboot clears.

## A host short of its runners

`CiHostRunnersOffline` (prometheus-rules-capacity.yaml, `fleet: fix`, so an agent gets it as a red) fires when a host has had fewer runners online than its topology slots (the exporter's `state="missing"` rows name them) for an hour. It covers owned hosts (`config.json` rates, basis owned) and powered hosts the governor reads as running, and skips the opt-in windows pool. The slots include the repo-scoped runners (`ci_repo_runners`, such as `<host>-dotfiles-private-1`), which take only their one repo's jobs, so a dead one queues that repo's jobs even while the host's org slots are idle. Only runners a topology slot names count as online, so a runner registered by hand cannot hide a dead slot. The exporter's `github_runner_state` rows name the slot: `state="missing"` means no runner of that name registered (for a repo runner, its `--tags linux-ci` play has not run on the host since the slot was added), `state="offline"` means it registered and its unit is down. For an offline one, check `systemctl status 'actions.runner.*'` on the host: a unit disabled by hand needs either starting again or an inventory change and a re-rendered topology in one PR, never an inventory left saying more than the host runs.

## A host stuck starting or stopping

`CiHostPowerStuck` (prometheus-rules-capacity.yaml, `fleet: fix`, critical) fires when the governor has reported a powered host as `starting` (EC2 `pending`) or `stopping` for 15 minutes; both normally clear inside one scrape. Nothing else shows it: the command-center ci pools row leaves out powered hosts not reported running. Read the instance first: `aws ec2 describe-instances --profile bnb --region us-east-2 --instance-ids <id> --query 'Reservations[].Instances[].[State.Name,StateReason.Message]'` (the id is in `ansible/inventory.yml`). If EC2 agrees it is stuck, a hung stop takes `aws ec2 stop-instances --force` on that id, and a hung start takes a stop and lets the governor start it again or pass to the next host. If EC2 says running or stopped and the metric does not, the governor's view is stale: check its log (`kubectl -n monitoring logs deploy/ci-runner-governor`) for the EC2 describe error.

## A small job on a whole slot

`CiSmallJobOnWholeSlot` (prometheus-rules-capacity.yaml, `fleet: fix`) fires when a light or heavy job has run 10 minutes on a whole Unity slot (`<host>-unity-pool-<n>`, from `ci_runner_job`) of a host that has light or heavy seats. A small job's one path there is a seat (Slots and seats, above), so the slot still carries a small kind's label. Read the runner's labels (`github_runner_state{name="<runner>"}`); the topology should give it none (`apps/ci-topology/topology.json`). A stale label from before the host's seats goes at the slot's next governor swap; to clear it at once, apply the host's slots (Apply the play, `--tags unity-ci`), which resets every slot's labels to the topology. If the topology itself gives the slot the kind, the host's `ci_seat_kinds` lost it: put it back and re-render.

## A small job waiting for a seat

`CiSmallJobQueuedTooLong` (prometheus-rules-capacity.yaml, `fleet: fix`) fires, one alert per kind, when a light or heavy job has waited 15 minutes for a seat, for 5 minutes. The seats look down because they sit withheld until the governor lends their slot (Slots and seats, above), so read the governor first: `kubectl -n monitoring logs deploy/ci-runner-governor --since=30m`. Lends that go out and come straight back ("a GitHub job it takes has waited ...") were hc-801; no lend while the kind waits means an older GitHub or Forgejo wait holds the slots, or a HOT or FULL host does. The seat units themselves: `systemctl status 'actions.runner.*-light-*'` on the host.

## A job no runner serves

`CiJobUnserved` (prometheus-rules-capacity.yaml, `fleet: fix`) fires when a job has waited 30 minutes for a label set that no registered runner its repo may use carries (the exporter's `github_actions_job_waiting{pool="unserved"}`; offline runners count, so a stopped host is not this). The alert names the repo, the job and the labels it asked for. Either the workflow asks for a label no slot has (fix the `runs-on`), or the slot that should take it is not in the inventory (add it there and re-render the topology). A repo-scoped runner is read only for a repo a topology slot names (`repo:` in `ci_pinned_runners`) or `RUN_REPOS`. The other wait classes: a cap name (a slot can take it), `github-hosted`, and `jobless` (GitHub gave the run no jobs).

## Not CI hosts: asus-laptop, hp-victus and razer-laptop

asus-laptop and hp-victus are service hosts, and razer-laptop (2026-11-18) is an agent host; all three are in `no_ci_hosts` (`ansible/inventory.yml`, which says why) and carry no CI of any kind: no Unity slots, no light/heavy runners, no Forgejo runner replica. `scripts/render-ci-topology.py` fails if one appears in a CI group. Before placing any work on a host, run `scripts/host-headroom.py <host>` and quote its load per CPU, temperature and memory. Do not add any of them back.
